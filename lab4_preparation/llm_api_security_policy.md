# Політика безпечного використання LLM API

**Команда:** гіпотетична команда розробки освітньої платформи (5–10 розробників)
**Сфера дії:** усі сервіси, що викликають Gemini API або інші LLM API, включно з прототипами, ноутбуками Colab і CI.
**Версія:** 1.0

## 1. Ключі та облікові записи
1. API-ключі ніколи не зберігаються в коді, ноутбуках, тікетах чи чатах. Локально — тільки `.env` (є в `.gitignore`), у Colab — Secrets, у продакшні — менеджер секретів (Secret Manager / GitHub Actions secrets).
2. Окремі ключі для середовищ dev / staging / prod і для кожного сервісу. Ключ prod недоступний розробникам.
3. Для ключів обмежуються API, IP або referrer, якщо це підтримує провайдер.
4. Ротація ключів — щонайменше раз на 90 днів і негайно при підозрі на витік. У репозиторії увімкнено secret scanning і pre-commit хук (наприклад, gitleaks).
5. Бюджетні ліміти й сповіщення про витрати налаштовуються для кожного проєкту.

## 2. Дані, що передаються в модель
1. Заборонено надсилати в API паролі, токени, персональні дані студентів (ПІБ + оцінки, контакти), медичні та фінансові дані без анонімізації.
2. Перед відправленням логи й документи проходять маскування (e-mail, телефони, номери документів).
3. Для продакшн-даних використовується лише платний рівень API з умовами, що виключають використання запитів для навчання моделей.
4. Усі промпти й відповіді журналюються без чутливих полів і зберігаються не довше 30 днів.

## 3. Захист від prompt injection
1. Системні інструкції містять чіткі межі ролі, заборону розкривати інструкції та приклади правильних відмов.
2. Недовірений вміст (документи RAG, листи, веб-сторінки, відповіді інструментів) обгортається розмежувачами і явно позначається як дані, а не команди.
3. Принцип найменших привілеїв для агентів: кожен інструмент має мінімальні права (лише читання, конкретний ресурс). Дії з побічними ефектами (надсилання листів, запис у БД, PR, платежі) вимагають підтвердження людиною.
4. Модель не повинна сама формувати URL з даними. Автоматичне відображення зовнішніх зображень і посилань у відповідях вимкнено або обмежено allowlist доменів.
5. Вивід моделі завжди вважається недовіреним: валідація JSON-схемою, екранування перед вставкою в HTML/SQL/shell, заборона `eval` згенерованого коду поза пісочницею.

## 4. Згенерований код
1. Згенерований код проходить такий самий code review і CI (лінтери, тести, SAST), як і написаний вручну.
2. Перед встановленням перевіряється, що рекомендовані пакети існують і є офіційними (захист від slopsquatting).
3. Код, отриманий від моделі, не виконується з правами продакшн-середовища.

## 5. Якість, вартість і стабільність
1. Для кожного виклику задаються таймаут, повтори з експоненційною затримкою та обмеження `max_output_tokens`.
2. Моделі обираються за потребою: швидка модель для класифікації, потужна — для складного аналізу. Рішення фіксується в README сервісу.
3. Зміни промптів версіонуються в Git і проходять регресійний набір тестових запитів (golden set).

## 6. Інциденти
1. Підозра на витік ключа: негайне відкликання ключа, ротація, аналіз журналів, повідомлення тимліда протягом 1 години.
2. Виявлена prompt injection: збереження прикладу, додавання його до регресійного набору, оновлення фільтрів і системних інструкцій.
3. Раз на семестр проводиться red teaming основних LLM-функцій платформи.

## 7. Відповідальність
* Розробник — дотримання політики у своєму коді.
* Тимлід — перегляд доступів і ключів щокварталу.
* Відповідальний з безпеки — оновлення політики відповідно до OWASP Top 10 for LLM Applications.
