## Крок 2. Chain-of-Thought: аналіз і рефакторинг коду

**Промпт:**
```text
Виступи в ролі досвідченого Python-розробника та code reviewer'а. Проаналізуй надану функцію. Твоя відповідь має складатися з трьох частин:
1. **Аналіз коду:** Покроково проаналізуй логіку, стиль та потенційні проблеми у коді.
2. **Пропозиції щодо покращення:** Запропонуй конкретні зміни для покращення читабельності (згідно з PEP 8), ефективності та надійності коду.
3. **Відрефакторена версія:** Надай кінцеву, покращену версію коду з коментарями, що пояснюють зміни.
Використовуй техніку Chain-of-Thought для першої частини (Аналіз коду), міркуючи покроково. Ось код для аналізу:

def CalculatePrice(items_list):
  total = 0
  for i in range(len(items_list)):
     if items_list[i] > 100:
         total += items_list[i] * 0.9 # 10% discount
     else:
       total += items_list[i]
  # special new year tax
  total = total * 1.05
  return total

```

**Результат:**
```text
Ось детальний огляд вашого коду з позиції досвідченого Python-розробника.

1. Аналіз коду

Функція приймає список цін, застосовує знижку 10% до товарів дорожчих за 100 одиниць, підсумовує результат і додає 5% податку. З погляду стилю код порушує стандарт PEP 8: назва функції написана в стилі PascalCase замість snake_case, відступи непослідовні (2, 3 та 4 пробіли), а перед рядковим коментарем бракує подвійного пробілу. Логіка ітерації через range(len(...)) є неідеоматичною для Python і погіршує читабельність. Також у коді присутні «магічні числа» (100, 0.9, 1.05), відсутня типізація (type hints), документація (docstring) та перевірка вхідних даних (наприклад, на від'ємні значення чи точність обчислень з плаваючою комою для фінансів).

2. Пропозиції щодо покращення

Дотримання PEP 8:
- Перейменувати функцію на calculate_price (snake_case).
- Вирівняти всі відступи до стандартних 4 пробілів.
- Додати два пробіли перед рядковими коментарями (або перенести їх вище/прибрати зайві завдяки зрозумілим іменам).

Ідіоматичність (Pythonic way) та ефективність:
- Замінити for i in range(len(items_list)): на пряму ітерацію елементами або використати вбудовану функцію sum() із генераторним виразом, що працює швидше та виглядає лаконічніше.

Читабельність та гнучкість:
- Винести «магічні числа» у параметри за замовчуванням або константи (поріг знижки, коефіцієнт знижки, податкова ставка).
- Додати docstring та анотації типів (typing / вбудовані типи Python 3.9+), щоб розширити підтримку будь-яких ітерабельних об'єктів (Iterable[float]), а не лише списків.

Надійність:
- Додати базову валідацію (наприклад, виклик ValueError, якщо ціна товару від'ємна).
- Округлювати кінцевий результат (наприклад, до 2 знаків після коми) через особливості арифметики чисел з плаваючою комою (float), або використовувати decimal.Decimal для критично точних фінансових розрахунків.

3. Відрефакторена версія

from collections.abc import Iterable

# Виносимо "магічні числа" у константи для легкого керування бізнес-логікою
DISCOUNT_THRESHOLD = 100.0
DISCOUNT_RATE = 0.10      # 10% знижка
NEW_YEAR_TAX_RATE = 0.05  # 5% новорічний податок


def calculate_price(
    prices: Iterable[float],
    discount_threshold: float = DISCOUNT_THRESHOLD,
    discount_rate: float = DISCOUNT_RATE,
    tax_rate: float = NEW_YEAR_TAX_RATE,
) -> float:
    """Обчислює загальну вартість товарів зі знижкою та податком.

    Для кожного товару, ціна якого перевищує поріг, застосовується знижка.
    До загальної суми додається фіксований податок.
    """
    subtotal = 0.0

    # Пряма ітерація по елементах замість range(len(...))
    for price in prices:
        if price < 0:
            raise ValueError(f"Ціна не може бути від'ємною: {price}")

        # Застосовуємо тернарний оператор для лаконічності
        discounted_price = price * (1 - discount_rate) if price > discount_threshold else price
        subtotal += discounted_price

    total = subtotal * (1 + tax_rate)

    # Округлення до 2 знаків для уникнення артефактів float (наприклад, 105.00000000000001)
    return round(total, 2)

Ключові переваги оновленого коду:
- Підтримує не лише list, а й будь-який ітерабельний об'єкт (tuple, set, генератор) завдяки Iterable[float].
- Параметри за замовчуванням дозволяють змінювати відсотки чи поріг без переписування тіла функції.
- Безпечна обробка помилкових даних (від'ємних цін) і передбачуване форматування грошової суми на виході.
```

## Крок 3. Симуляція Tree-of-Thought

**Промпт:**
```text
Проаналізуй наступну задачу. Твоя відповідь має складатися з таких кроків:
1. **Генерація гілок (підходів):** Запропонуй три принципово різні технічні підходи для вирішення поставленої задачі.
2. **Оцінка гілок:** Для кожного підходу детально проаналізуй його переваги (Pros) та недоліки (Cons) в контексті освітнього сайту з малим бюджетом.
3. **Вибір оптимального шляху:** На основі твого аналізу зроби висновок і обґрунтуй, який з підходів є найбільш оптимальним у даній ситуації.
Ось задача: "Компанії потрібно розробити систему для автоматичної модерації коментарів на освітньому сайті. Коментарі можуть бути токсичними, спамом, не по темі або нормальними. Які три різні технічні підходи можна використати для створення такої системи? Оціни їхні переваги та недоліки і вибери оптимальний для освітнього сайту з невеликим бюджетом."
```

**Результат:**
```text
1. Генерація гілок (підходів)

Для вирішення задачі автоматичної модерації коментарів (токсичність, спам, не по темі, норма) можна застосувати три принципово різні технічні підходи:

Підхід 1: Евристично-статистичний (Rule-based + Класичне ML)
Комбінація детермінованих правил (регулярні вирази для посилань/телефонів, словники стоп-слів) та легких алгоритмів машинного навчання (TF-IDF векторизація + логістична регресія, Naive Bayes або SVM). Для перевірки «не по темі» використовується обчислення лексичної подібності (наприклад, косинусної подібності TF-IDF) між коментарем і текстом уроку.

Підхід 2: Локальні компактні нейромережі (Self-hosted Small Transformers)
Використання попередньо навчених багатомовних мовних моделей типу BERT (наприклад, DistilBERT, XLM-RoBERTa-small або легких моделей ембедінгів типу multilingual-e5-small), донавчених (fine-tuned) на власних розмічених даних. Для економії ресурсів моделі квантуються і запускаються через ONNX Runtime на власному CPU-сервері.

Підхід 3: Хмарні легкі LLM через API (Zero/Few-shot Prompting)
Використання готових швидких і дешевих комерційних генеративних моделей (класу GPT-4o-mini, Gemini Flash, Claude Haiku) через REST API. У промпт передається контекст уроку (назва, короткий опис) та сам коментар, а модель повертає структуровану відповідь (JSON) із категорією.

2. Оцінка гілок (у контексті освітнього сайту з малим бюджетом)

Підхід 1: Rule-based + Класичне ML
Переваги (Pros):
- Мінімальна вартість інфраструктури (OPEX): Система може працювати на найдешевшому VPS ($5/міс) разом з основним бекендом.
- Миттєва швидкість роботи: Час обробки одного коментаря — до кількох мілісекунд, що дозволяє модерувати коментарі синхронно в момент відправки.
- Незалежність: Немає прив'язки до зовнішніх сервісів чи ризику раптового зростання рахунків через атаку ботів.
Недоліки (Cons):
- Провал у визначенні «не по темі»: Освітні коментарі часто короткі («Дякую, все зрозуміло!», «А чи буде продовження?»). Вони не містять ключових слів з уроку, тому статистичні методи помилково вважатимуть їх оффтопом. І навпаки, спам із ключовими словами уроку пройде фільтр.
- Слабке розуміння контексту та сарказму: Алгоритми не вловлюють приховану токсичність, завуальовану лайку («заміна літер символами») чи конструктивну критику (яка може містити негативні слова, але не є токсичною).
- Висока вартість підтримки правил: Базу стоп-слів і регулярних виразів доведеться постійно оновлювати вручну, а для ML-моделі — десь брати розмічений датасет саме для освітньої тематики.

Підхід 2: Локальні компактні нейромережі (Self-hosted Transformers)
Переваги (Pros):
- Передбачувана вартість масштабування: Фіксована ціна за оренду сервера без плати за кожен запит (вигідно при мільйонах коментарів).
- Висока точність (після навчання): Трансформери добре розуміють семантику, синоніми, сленг та складну токсичність.
- Приватність даних: Коментарі студентів не покидають периметр серверів компанії.
Недоліки (Cons):
- Високий поріг входу (CAPEX): Для сайту з малим бюджетом найняти ML-інженера, зібрати й розмітити тисячі прикладів (особливо для специфічної категорії «не по темі» під різні курси) — це надто дорого і довго.
- Вимогливість до ресурсів: Навіть квантована модель на CPU споживає значно більше RAM (від 1–2 ГБ лише під модель) та процесорного часу, що збільшує вимоги до сервера.
- Складність визначення оффтопу через ембедінги: Як і в Підході 1, просте порівняння векторів коментаря і статті дасть багато хибних спрацьовувань на коротких загальноосвітніх репліках («Супер пояснення», «Повторіть момент на 5-й хвилині»).

Підхід 3: Хмарні легкі LLM через API
Переваги (Pros):
- Мінімальна вартість і час розробки (CAPEX): Інтеграція займає 1–2 дні роботи звичайного бекенд-розробника. Не потрібні ні ML-фахівці, ні збір датасетів для старту.
- Найкраще розуміння «не по темі» та контексту: LLM легко відрізняє ввічливе «Дякую за урок!» (норма) від «Яка сьогодні погода?» (оффтоп), якщо в промпті передати тему уроку. Також чудово розуміє сарказм, помилки друку та багатомовність (суржик, українська, англійська).
- Гнучкість: Зміна правил модерації (наприклад, дозвіл чи заборона посилань на інші джерела) робиться редагуванням тексту промпту за 5 хвилин без перенавчання моделей.
Недоліки (Cons):
- Змінні витрати (OPEX) та ризик DDoS: Ви платите за кожен токен. Якщо сайт атакують спам-боти, які згенерують тисячі коментарів за хвилину, рахунок за API зросте (потрібен базовий rate-limiting та капча).
- Вища затримка (Latency): Відповідь API триває 0.5–2 секунди. Краще реалізовувати модерацію асинхронно (коментар падає в чергу, перевіряється у фоні й публікується/приховується).
- Передача даних третій стороні: Тексти коментарів відправляються на сервери провайдера ШІ (хоча більшість API-провайдерів не використовують API-дані для навчання своїх моделей).

3. Вибір оптимального шляху

Для освітнього сайту з невеликим бюджетом найоптимальнішим є Підхід 3 (Використання хмарних легких LLM через API), доповнений елементарним захистом на рівні бекенду (rate-limiting, базовий фільтр відвертого спаму з посиланнями до виклику API).

Обґрунтування вибору:
- Економіка проєкту (CAPEX vs OPEX): Головна стаття витрат при обмеженому бюджеті — не вартість токенів, а зарплата розробників і час виходу продукту (Time-to-Market). Освітній сайт зазвичай генерує помірний потік коментарів (сотні або кілька тисяч на день, а не мільйони). Сучасні легкі моделі (на кшталт Gemini Flash або GPT-4o-mini) коштують лічені центи за тисячі запитів — місячний рахунок за API для такого сайту складе $1–$10, що дешевше навіть за оренду додаткового сервера для локальної нейронки (Підхід 2) і в десятки разів дешевше за оплату праці ML-інженера.
- Вирішення найскладнішої вимоги («не по темі»): Класичне ML і прості локальні класифікатори провалюються саме на розрізненні коротких позитивних коментарів («Гарний урок!») та реального оффтопу («Продам ноутбук» або «А коли вийде новий фільм?»). LLM вирішує цю задачу «з коробки» на основі загального розуміння мови й переданого заголовка/опису уроку.
- Масштабованість у майбутньому: Якщо сайт виросте настільки, що витрати на API стануть відчутними (наприклад, перевищать $100–200/міс), компанія вже матиме накопичену та розмічену самим API базу реальних коментарів. На її основі в майбутньому можна буде легко та дешево навчити власну локальну модель (перехід до Підходу 2), але на старті вкладати в це ресурси економічно недоцільно.
```

def AverageGrade(grades):
    total=0
    for g in grades:
        total+=g
    average = total / len(grades) - 1
    if average >= 90: return "A"
    elif average >= 75:
        return "B"
    elif average > 60:
        return "C"
    else:
        return "F"
